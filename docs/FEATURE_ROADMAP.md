## 5. 功能二：Provider 原生结构化工具调用

### 目标

优先使用 Provider 原生 Tool Calling，减少文本工具协议产生的解析失败、参数丢失和误判。

### 建议结构

```python
@dataclass
class ToolCall:
    id: str
    name: str
    arguments: dict[str, Any]

@dataclass
class AssistantResponse:
    text: str | None
    tool_calls: list[ToolCall]
    usage: TokenUsage | None
    stop_reason: str | None
```

### 开发任务

- [ ] 定义 Provider 无关的 `ToolCall`、`AssistantResponse` 和 `TokenUsage`。
- [ ] 把现有工具签名转换成统一 JSON Schema。
- [ ] 改造 Fake Provider，建立确定性契约测试。
- [ ] 改造 DeepSeek/Anthropic 兼容 Provider。
- [ ] 改造 OpenAI Responses 兼容 Provider。
- [ ] 改造 Ollama Provider。
- [ ] 保留文本协议作为不支持原生工具调用时的回退方案。
- [ ] 支持响应中同时存在文字和工具调用。
- [ ] 支持多个工具调用及各自的调用 ID。
- [ ] 将参数校验继续集中在 Tool Executor。
- [ ] 记录工具调用 ID，避免重试时重复执行。
- [ ] 为截断响应、非法 JSON、未知工具和参数缺失添加测试。
- [ ] 在报告中统计结构化调用率和解析失败率。

### 验收标准

- [ ] 支持原生调用的 Provider 不再经过文本解析器。
- [ ] Agent Loop 只消费统一的 `AssistantResponse`。
- [ ] 同一工具调用 ID 最多产生一次副作用。
- [ ] Provider 不支持原生工具时可以自动降级。
- [ ] 原有 Fake Provider 基准仍保持确定性。

### 完成意义

直接提高模型调用工具的可靠性，同时让 Agent Loop 与具体模型厂商解耦，为并行工具和流式响应奠定基础。

## 7. 功能四：Docker 沙箱执行

### 目标

将高风险 Shell 命令迁移到受限容器中，使“副作用可控”具备操作系统级隔离基础。

### 建议接口

```python
class ExecutionBackend(Protocol):
    def run(
        self,
        argv: list[str],
        cwd: Path,
        timeout: float,
        policy: ExecutionPolicy,
    ) -> CommandResult:
        ...
```

### 开发任务

- [ ] 从 `run_shell` 中抽象 `ExecutionBackend`。
- [ ] 保留 `LocalExecutionBackend` 并显示安全级别。
- [ ] 实现 `DockerExecutionBackend`。
- [ ] 默认只挂载当前工作区。
- [ ] 使用非 root 用户运行命令。
- [ ] 默认禁止容器访问网络。
- [ ] 支持只读与读写工作区模式。
- [ ] 限制 CPU、内存、进程数、时间和输出大小。
- [ ] 不挂载用户主目录、SSH 配置和宿主凭据。
- [ ] 不向容器传入模型 API Key。
- [ ] 确保超时或取消后清理全部子进程和容器。
- [ ] 在运行报告中记录镜像、资源限制和网络策略。
- [ ] 增加路径逃逸、网络访问、资源耗尽和密钥读取测试。
- [ ] 增加 Docker 不可用时的明确诊断。

### 验收标准

- [ ] 容器内无法读取工作区外的宿主文件。
- [ ] 禁网模式下不能访问公网。
- [ ] 无法读取宿主 `.ssh` 和 `.env` 中的模型密钥。
- [ ] 超时后无残留进程或容器。
- [ ] 容器产生的文件改动可以被工作区差异审计捕获。
- [ ] 本地后端与 Docker 后端共用统一结果结构。

### 完成意义

这是项目最重要的安全增强之一，能把应用层允许列表和审批升级为可验证的执行隔离。

## 11. 跨功能约束

七项功能开发过程中应共同遵守以下原则：

- 模型输出不能直接绕过 Tool Executor 操作宿主机。
- API Key 不进入提示词、工具结果、运行报告和 CI 日志。
- 新功能必须同时考虑 Windows 与 POSIX 行为。
- 状态写入尽量采用原子操作，并考虑进程中断。
- 运行结果必须能够关联任务、Provider、模型、提交和工作区指纹。
- 评测结果与单元测试结论必须明确区分。
- 新增遥测默认只记录元数据和摘要，完整内容必须显式启用。
- 不应在未实现前在 README 或简历中宣称功能已经完成。

## 13. 最终完成定义

七项完成后，Allright 应能够做到：

- 在任务开始前自动诊断本地环境和 Provider。
- 使用统一的原生结构化协议调用工具。
- 在多个操作系统上持续通过自动化验证。
- 在隔离环境中运行高风险命令。
- 使用真实模型和固定任务进行可重复评测。
- 展示 Token、成本、耗时、工具和恢复指标。
- 在终端持续显示进度，并允许安全取消和恢复。

目标项目描述：

> Allright 是一个面向本地代码仓库长链路任务的可诊断、可恢复、可审计、可隔离、可评测代码 Agent Harness，支持多模型接入、结构化工具调用、分层记忆、检查点恢复、跨平台验证和运行成本分析。
